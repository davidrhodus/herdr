---
title: Connecting machines
description: Work across Local and saved SSH machines in one Herdr window, with shared agent navigation and independent reconnects.
---

Keep your local work and remote agents in one Herdr window. Save an SSH machine once, then switch between its workspaces and Local without opening another client. The agent list includes connected machines, so you can see where work is running and which agent needs an answer.

Each machine keeps its own Herdr server, sessions, and running processes. A lost connection to one machine does not disconnect the others.

Herdr requests SSH compression to reduce screen-update traffic on limited connections. This works with older compatible Herdr servers and does not change how typing or other input is delivered. Herdr's `-C` option overrides `Compression no` in your SSH config. If SSH reuses an existing connection through an external ControlMaster, that connection keeps its original compression setting.

## Add and manage servers in the TUI

Click **＋ server** at the bottom of the sidebar, or open **Servers** from the
main menu or **Settings → Machines**. Enter a hostname, SSH config alias, LAN address, or Tailscale name in
**Host / IP**, and your remote login in **Username**. Leave Username blank to
use your SSH configuration or local username. Existing `you@hostname` addresses
also work. Give it an optional display name and click
**Connect**. Suggestions include literal SSH aliases and online Tailscale peers
when the Tailscale CLI is available.

Click **Browse Tailscale** beside Connect (or press Ctrl+T, the Control key on
Mac) to open the device browser. No terminal keyboard settings need to change.
It lists only devices that Tailscale reports as online, with their IPv4/IPv6
addresses. Type a name, hostname, or IP address in Search to narrow the list;
matching ignores letter case. Use Backspace to edit or Ctrl+U to clear the search.
Click a device or select it with Up/Down and Enter to fill Host / IP;
Herdr prefers its Tailscale DNS name and falls back to its IP address. The form
keeps your username and other settings, and does not connect until you choose
Connect. Escape or Back returns to the form.

Use **Refresh** or press Ctrl+R to fetch current status without clearing your
search. If Tailscale is missing,
disconnected, or signed out, the browser explains how to retry; manual entry
still works. Online status comes from Tailscale and does not verify SSH access.
Herdr can use the CLI bundled in the macOS Tailscale app, even when `tailscale`
is absent from PATH.

Setup runs inside the dialog. OpenSSH asks for host-key approval, a key
passphrase, password, or MFA response there. Herdr then checks the installation,
lets you choose an existing remote session, or prepares a new one. If installing
or replacing Herdr is necessary, a separate confirmation shows the source and
destination. Replacing a running server asks explicitly before stopping its
pane processes. You can cancel setup without leaving the TUI.

Expand **Advanced** (or press Alt+A) for a custom SSH port, a key-file path on
this computer, and an explicit remote session. Tab moves between fields; arrow
keys and Enter choose suggestions. Key-file paths stay local and are never
included in the shared server list. Each computer needs working SSH access.

Right-click a saved server's sidebar header, or select it in **Servers**, to
reconnect, update, rename, enable, disable, or remove it. Removing a profile leaves its
remote sessions running. Failed setup retains the form so you can correct it
and retry. Ctrl+G cancels an active setup; Escape closes a form.

### Recovering SSH authentication

Click a saved server's name or authentication-required badge to open SSH login
and automatic key repair directly in the TUI. Background failures stay quiet;
they never open a password prompt while you are working. Network failures retry
normally, and host-key mismatches remain rejected.

**Automatic SSH key** is enabled by default in Add server for Linux/macOS hosts.
Herdr enrolls and verifies the dedicated key before querying sessions or installing
the remote build, so those steps reuse key authentication after one password entry.
Click the checkbox or press Ctrl+K to disable enrollment for a server that requires
another authentication method. The CLI opt-in is `herdr machine add <target> --setup-key`.

For password-free reconnects, choose **Servers → your server → Set up SSH key
(no more passwords)…**. Confirm, then enter the existing SSH password once in
the embedded SSH prompt if requested. Herdr generates a dedicated Ed25519 key
without a passphrase in private local storage, adds only its public key to that
account's `~/.ssh/authorized_keys`, and verifies a fresh connection before saving
the local identity setting. It then repairs the saved server connection and starts
a stopped Herdr daemon. Existing keys and saved server profiles are preserved.
Repeating setup reuses the same key and avoids duplicate authorized-key entries.
No Rust installation, `ssh-copy-id`, or manual shell commands are needed.

Private keys never sync to another manager: run this setup once on each computer.
The server must allow public-key authentication without additional MFA for a
fully unattended reconnect. The CLI equivalent is `herdr machine setup-key <label-or-id>`.

Choose **Reconnect / authenticate** in the server's menu to complete native SSH
authentication inside the TUI, prepare the matching Herdr executable, and start
a stopped server. Keys stay with OpenSSH; password-only access can require a
fresh password when its shared SSH connection expires. The CLI alternative is
`herdr machine reconnect <label-or-id>`.

For an existing Linux server, open **Servers → your server → Update Rust build…**.
Enter the SSH password if requested, then approve installing the bundled build.
Existing sessions use the normal restart approval flow; the saved profile is
preserved. The CLI alternative is `herdr machine update <label-or-id>`.
`herdr machine status [<label-or-id>] [--json]` performs fresh, noninteractive
checks. **Reachable** means the remote server is available now; it does not
mean every open TUI is connected.

On Linux and macOS with `remote.manage_ssh_config=true`, Herdr shares an approved
OpenSSH connection across setup, the sidebar, and saved-machine API commands.
The connection uses `ControlPersist 600` (10 minutes of idle time); this is not
MFA validity. Active connections can remain open, while corporate policy, the
SSH server, or the network may end them sooner. Windows and unmanaged SSH do
not share password-only or MFA approval with background connections; configure
a key or SSH agent for unattended reconnects. First-contact trust is requested
inside setup. Changed host keys remain rejected, and background connections
never accept a new key automatically.

Saved TUI connections check whether an existing shared SSH connection can open a new channel. CLI status and API commands check only after an initial read-only connection failure. If reuse fails while a fresh connection to the same host succeeds, Herdr retires the old connection from reuse and reconnects. Existing channels stay open. A fresh connection that needs authentication or rejects the host key does not trigger this recovery. API commands retry connection setup at most once and never repeat a request that may already have changed remote state.

### Install a local Rust build on Linux hosts

For a customized checkout, run `just build-linux-bundle`. This builds static
Linux x86_64 and ARM64 executables from the same source, then embeds them in
`target/release/herdr`. Install that manager executable on your computer.
Adding a Linux server in the TUI installs the matching embedded executable over
SSH, without fetching a published release or requiring Rust on the server.
The setup approval identifies the bundled Rust build being installed.

Local bundles have a source-specific version. Setup replaces a published or
different local executable after approval, and reuses an already matching
installation. Existing running sessions follow the normal server update and
restart approval flow. Local builds never fall back to a published binary for
a missing platform. `HERDR_REMOTE_BINARY` remains an explicit override.

The build recipe installs the Rust musl targets and uses Rust's bundled linker;
it needs no Docker or Zig. The resulting Linux payloads require no glibc and
support both glibc and musl distributions. Rebuild the bundle after source changes.

## Import a running terminal on a server

Click **Import sessions** beside a saved server in the sidebar to open its
terminal browser directly. Narrow sidebars use **Import**; expand the sidebar
if it is collapsed. You can also choose
**Servers → your server → Discover / import running terminals…**.
Discovery lists this SSH account's external Linux terminals in the same process
and mount namespace as Herdr, showing their TTY,
foreground program, working directory, and process count. Herdr's own terminals,
already-importing terminals, tmux/screen sessions, and other users' processes
are excluded. Refresh queries the selected server without changing its sessions.

If needed, choose **Enable import helper**. After approval, this installs the
distribution's `reptyr` package and a protected, root-owned Herdr helper. SSH and
administrator prompts stay in the TUI. Kernel tracing settings are not changed.

Select a terminal, review the transfer, then choose **Open** for its new workspace.
Administrator authorization may be requested there. The helper rechecks the
account, host boot, PID, process start time, session ID, and TTY after authorization.
It transfers the whole terminal using `reptyr -T`; the existing shell and programs
keep running, while the old terminal window loses control.

Closing the discovery dialog or disconnecting a manager does not cancel a started
transfer. If permissions prevent import, the new workspace keeps the diagnostic
and allows an explicit retry. Keep it open while a transfer is pending. Closing
an imported workspace closes that terminal. Screen history and Herdr agent
registration are not reconstructed, and the original processes do not receive
new Herdr environment variables. A full server shutdown does not make an imported
PID restartable; a later cold restore starts a normal shell instead of replaying
a stale process ID. A live daemon handoff preserves the running import proxy.

The browser works against every configured host and reports its capability.
Live process transfer is currently Linux-only and still depends on the host's
administrator/tracing policy. Other operating systems show an unsupported message.

The neutral APIs are `terminal.sessions.list` and `terminal.sessions.import`;
`herdr --machine <server> terminal-import list` exposes discovery from the CLI.

## Automatic background server-list sync

Enable a shared list once on an SSH account you control, for example
`herdr sync host` on Redie. Updated managers discover that account's opted-in
registry through their saved SSH connection and join automatically. Successful
`--remote` connections also qualify, even before that host has a saved profile.
This works in direct remote and non-shell client modes as well as the normal
manager UI; the current terminal surface stays selected. Simply
installing Herdr on an arbitrary server does not enable sharing. Both computers
must use the same hosting account. Different SSH aliases for that account are
recognized as one registry; if several distinct registries are available, choose
one in **Servers → Server-list sync**.

On macOS and Linux with a user service manager, the installed
`~/.local/bin/herdr` starts a per-user background service when the TUI opens.
You can also run `herdr sync auto` to enable automatic enrollment and start it.
When developing from `~/herdr`, `cargo run --release` copies the release executable
to a stable `~/.local/libexec/herdr-sync-agent` path for the background service,
preserving one previous background executable. Debug builds and isolated test namespaces do not install
login services.
The service keeps the launching terminal's `PATH` and `SSH_AUTH_SOCK` for initial
enrollment. These settings are refreshed when the UI opens again.
No SSH listener or incoming connection to either manager is required.
Server additions, renames, and removals sync about every 15 seconds even after
the TUI closes. Sleep, logout, or lost network access pauses exchanges; local
changes remain available and sync resumes after reconnecting. Linux uses the
existing user-login/linger policy and does not change it.

Private SSH keys remain on each computer. Background connections never ask for
passwords or accept changed host keys. Authenticate a server in the TUI once
and use automatic key setup for unattended access. Existing terminal sessions
are independent of syncing and service restarts.

### Restricted SSH credentials for sync

Updated managers automatically create a separate Ed25519 key for each shared
SSH target. The first enrollment uses the existing login once, without prompting
in the background, and adds only the new public key to the hosting account.
The Unix host must run this build and already be opted into hosting. Enrollment
does not update the server executable or enable hosting on another account.

Its `authorized_keys` entry uses OpenSSH `restrict` and a forced Rust dispatcher.
Only fixed registry-status and catalog-exchange requests are accepted. The key
cannot request a shell, execute arbitrary commands, transfer files, allocate a
PTY, forward ports, or forward an agent. The dispatcher is bound to the current
registry and a fixed state directory; SSH-supplied paths or extra arguments do
not change that binding. Existing terminal login keys remain independent.

The client uses an isolated SSH configuration with only the sync identity,
public-key authentication, and no multiplexed connection reuse. It verifies the
enrolled fingerprint, registry identity, and rejection of a forbidden command
before activating the credential. A missing, revoked, or broken active key
causes sync to fail; it never falls back to a terminal/login key. Upgrade older
hosts before using this transport. Private keys stay in the local private
`client/sync-keys` state directory and never sync to another computer. Terminal
access still has its normal SSH privileges; this restriction limits the sync
credential, not an attacker who controls the entire Mac account.

`herdr sync status --json` shows the selected source, last success or error,
registry identity when hosting, and background-service heartbeat. The sidebar has a clickable **Sync** status. Green means at least two distinct
restricted keys have fresh, matching server-list exchanges, including this
computer. Click it to see manager names (when Tailscale knows them), IPs, last
exchange ages, and full key fingerprints. Names and IPs are display hints;
fingerprints identify the credentials. Pending changes, stale or unavailable
reports, and active older clients using login keys prevent a green status.
Status updates automatically; **Refresh manager status (Ctrl+R)** checks again.
The shared host must run a build supporting manager status reports; older hosts
continue syncing but show an upgrade notice instead of verified status.
The screen also shows whether background sync is running.
The JSON `sync_key` field includes enrollment state and its public fingerprint. Use
`herdr sync background start|stop|status` to manage the login service.
**Stop sharing** / `herdr sync leave` preserves the local server list and disables
automatic enrollment until `herdr sync auto` or another explicit setup action.
Existing manual sources and approved direct pairings take precedence over
automatic enrollment. An abandoned Direct pairing with no peers or active
approval can recover through a discovered shared host; its offline edits and
deletion history are retained.

## Pair managers directly over Tailscale

Your desktop and laptop can share the server list directly, without choosing a
shared host or enabling SSH between the managers. Both computers need this
Herdr build and connected Tailscale. Keep both UIs open for initial approval;
the background sync service can maintain the pairing afterward.

1. On either computer, open **Servers → Server-list sync → Pair another manager over Tailscale**.
2. Choose **Find / refresh running managers**, select the other computer, and confirm the pairing request.
3. On the other computer, open the same screen. Compare the full matching code shown on both computers and approve the request.
4. Back on the first computer, confirm that the matching code agrees. The lists merge and automatic sync begins.

Incoming requests show a notice and remain in the pairing screen; they do not
interrupt terminal or SSH authentication input. Unfinished approvals expire
after three minutes. Pairing is remembered across UI restarts. Multiple UI
windows under the same OS user share one identity and the same pairings.

Paired managers reconnect using stable Tailscale device identities, including
after an IP or hostname changes. Additions, renames, enabled state, and removals
sync every 15 seconds while a manager UI or its background service is running. Offline changes remain
local until the other manager is available. **Sync paired managers now** forces
a round. **Forget** revokes a pairing; **Stop direct manager sync** forgets all
direct pairings on this computer. Neither action deletes your server list or
stops remote sessions.

Only server profiles sync. SSH keys, passwords, per-computer identity-file
paths, UI layouts, and selections remain local. Approving direct sync switches
that computer away from any previously configured shared-list host while
retaining its existing list and merge history.

Discovery checks for running Herdr managers on online Tailscale devices. If the
other computer does not appear, check that both UIs are running this build.
Restricted Tailscale policies must permit TCP port 45971 between the computers.
Herdr listens only on its Tailscale addresses, authenticates paired exchanges,
and opens no listener on LAN or public wildcard addresses. Changing this
computer's Tailscale identity revokes its pairings; pair again on the new identity.

## Sync the server list between computers

For a shared host that can remain available while either manager UI is closed,
open **Servers → Server-list sync**. Choose an existing saved server or
enter another SSH address to use as the shared-list host. Herdr prepares that
host through the same guided setup, merges its existing list, and starts
sharing. Repeat this one-time choice on your other computer. If the list should
live on the computer you are using, choose **Host on this computer** and enable
SSH access through your operating system.

The sharing screen shows the configured source, last successful sync, and any
connection error. It also provides **Sync now** and **Leave shared list**.
Leaving preserves your local list and running sessions.

The CLI remains available. Choose one reachable computer or server to hold the
shared list. On that computer, using the same OS user your clients will SSH into, run:

```bash
herdr sync host
```

On your other computers, join that host once:

```bash
herdr sync join you@desktop
```

Use an SSH config alias, LAN address, reachable WAN hostname, or Tailscale name.
For example, `herdr sync join you@desktop.your-tailnet.ts.net`. All participants
need a Herdr build with sync support and working SSH access. Sync uses SSH's
existing authentication, host-key checks, and encryption; it requires no cloud
account, web service, or additional listening port. The host's Herdr UI does not
need to be open: an SSH command exchanges the list using its installed binary.

The initial join merges both existing lists. Afterwards, adding, renaming,
disabling, or removing a machine synchronizes automatically while a UI is open
(every 15 seconds). Machine commands also attempt sync after saving. Run
`herdr sync now` to force a round, and `herdr sync status` to see the configured
host, last successful exchange, and any connection error. A failed initial join
keeps the selected source configured so a later round can retry.

The shared host automatically records recent SSH catalog exchanges. Its
`herdr sync status --json` output includes `managers`, with each source IP,
`last_exchange`, `recent`, and `in_sync`. A connection is `in_sync` only when
it recently sent the same complete catalog the host currently holds; the first
download alone does not establish this. Evidence expires after 60 seconds and
becomes out of date when the catalog changes. These are connection diagnostics,
not device identities: managers sharing both an address and credential share
an entry. Restricted keys have separate entries from older login-key clients.
Checking the shared host does not require SSH access to either manager, and
existing v1 clients contribute receipts without an update.
Receipts also identify `restricted_key` versus `legacy_ssh` authentication and
include the sync key's public fingerprint when the forced dispatcher was used.

The shared list includes machine IDs, labels, SSH targets, sessions, and enabled
state. SSH credentials and configuration, UI selection, and local terminal
state stay on each computer. SSH aliases must resolve and authenticate on each
computer; portable hostnames such as Tailscale names make this easier. Separately
created profiles retain their own IDs, including duplicate destinations.

Use an always-on host if both desktop and laptop should sync while the other
is asleep. When the host is unreachable, changes stay local and are uploaded
when a UI or sync command can reach it again. Edits to different machines merge;
concurrent edits to the same machine resolve by logical counter, then device
ID. Deletions win over stale edits, so an offline computer cannot resurrect a
removed machine. Adding the machine again creates a fresh ID.

`herdr sync leave` stops syncing and keeps the local machine list and all remote
sessions. Run it before choosing a different shared-list host. The shared list
is per SSH user, not per Herdr runtime session. Historical deletions are retained
up to 1,024 total records (including at most 64 live machines).


## Before you connect

You need normal SSH access to the remote machine. Guided setup checks this in
the TUI; you can also check it from a terminal:

```bash
ssh workbox
```

`workbox` can be a host from your SSH config. You can also use a target such as `ssh://you@server:2222`.

Multi-machine connections support Linux, macOS, and Windows clients connecting to Linux or macOS servers on x86_64 or aarch64, or Windows servers on x86_64. Interactive setup can install or update the complete remote package after confirmation; background reconnects only discover installed packages. See [Remote attach over SSH](/docs/persistence-remote/#remote-attach-over-ssh) for SSH configuration, authentication, and custom binaries.

## Add a machine from the CLI

Alternatively, run setup in an interactive terminal so Herdr can ask before installing or replacing anything:

```bash
herdr machine add workbox
```

In an interactive terminal, Herdr discovers running sessions: it selects the only running session, or lets you choose with Up/Down and Enter when several are running. Esc or Ctrl+C cancels. If a successful query finds no running sessions, setup uses `default`. If no Herdr installation is found, setup offers to install it for `default`. If an installed binary cannot report its sessions, setup reports the error; pass `--remote-session <name>` to select a session explicitly.

The sidebar shows the default session as `workbox`, the SSH host without any `user@` prefix. Add `--label "Build machine"` to choose a different name. A machine profile targets one remote session; it does not combine every session on the host. Non-interactive commands use `default` unless `--remote-session` is supplied.

To skip discovery and use a specific session, add `--remote-session`:

```bash
herdr machine add workbox --remote-session agents
```

Without `--label`, this machine shows as `workbox/agents`. If the default name is already taken, `machine add` asks you to pass `--label`.

On Windows servers, setup also checks executables used by Herdr processes owned by the SSH user. It validates their capabilities before reuse, so a compatible running build can be used even when SSH's `PATH` points to an older installation.

Herdr checks both the installed binary and the running server. It starts the requested background server before saving the profile. Compatible client and server versions do not have to match. Missing or incompatible installations go through an approval-based setup. When the running server needs replacement, setup asks before stopping it and its pane processes, then starts the compatible server. The default answer is No. If installation and replacement are both needed, one confirmation covers them. `machine add` does not use experimental live handoff. Cancelling or failing setup leaves the profile unsaved.

Run `herdr` to open the UI. If a local client is already open, added and enabled machines normally appear within a second and connect in the background without changing your selection. An in-progress machine switch finishes before profile changes are applied. The remote server keeps running after setup exits.

## Switch between machines

Choose a machine or one of its workspaces in the sidebar. The selected machine receives your pane input and terminal size, and supplies the visible terminal content and graphics. Other connected machines keep updating their workspace information, agent states, and notifications without streaming their pane screens.

Click the arrow beside any machine to collapse or expand its workspace list without switching away from your current workspace. This also works while that machine is reconnecting.

For keyboard navigation, press `prefix+w`, then use the workspace navigation keys (Up/Down by default) to highlight workspaces across connected machines in sidebar order. Enter activates the highlighted workspace; Esc or the prefix key cancels without switching. Compact and expanded sidebars reveal the highlighted row, including under a collapsed machine. On desktop, navigation wraps at the ends; the mobile switcher stops at the first or last workspace. Disconnected machines are skipped.

When highlighting a workspace on another machine, press Enter before using other keyboard actions. This prevents pane, tab, workspace, or custom-command shortcuts from acting on the current machine by mistake. Clicking cancels a remote desktop keyboard preview. Expanded sidebars respect each machine's collapsed worktree groups.

Local opens immediately on startup without waiting for SSH connections. Selecting Local also cancels an unfinished remote switch without waiting for the remote machine to reply. If Local itself is reconnecting, your selection resumes when it is ready. Local accepts input once its fresh screen and terminal settings are ready. A stalled machine cannot hold up another machine's input. Multiple Herdr clients can also view different tabs on the same server independently; see [Client and server](/docs/concepts/#client-and-server) for shared-tab sizing.

When a connection is lost, the last workspace and agent state remains visible but dimmed. That is cached information, not live state. Input and navigation into those cached panes stay disabled until a fresh connection and matching screen arrive. Reconnecting never takes selection away from the machine you are using.

## Rename, disable, or remove

Read profile IDs from the list rather than deriving them from labels or hostnames:

```bash
herdr machine list
herdr machine rename <profile-id> --label "New name"
herdr machine disable <profile-id>
herdr machine enable <profile-id>
herdr machine remove <profile-id>
```

For scripts, add `--json` to `machine list`.

Renaming changes the displayed label without reconnecting. Disabling keeps the profile for later; removing forgets it. Both disconnect only that machine from the client and leave its remote sessions and agents running, even if the host is unreachable.

Removing or disabling the machine you are viewing returns you to Local. If Local is unavailable, Herdr shows that and retries its connection instead of selecting a different remote machine. With enabled saved machines, the client can remain usable even if Local fails or restarts.

## Connection problems

- **Reconnecting:** Herdr retries automatically after a network interruption, sleep, or SSH failure. Repeated failures increase the delay up to two minutes; brief successful connections do not reset it. A connection must remain healthy for a minute before the next interruption gets a fast retry. SSH connections are checked for application-level activity and probed when quiet, so a broken connection does not stay Online indefinitely. Local detects native connection closure or failure instead of using remote health probes.
- **Attention:** The target needs an action such as authentication, host-key approval, or a compatible server. Other machines remain usable. **`! auth`** means authentication failed; **`! error`** indicates another issue. Click the badge to retry; if it fails, a notice shows the fresh error and a CLI command. In a collapsed sidebar, either appears as `!`.
- **Saved-machine file error:** An unreadable or invalid catalog leaves current connections unchanged. Herdr shows a notice and automatically retries reading it.

When both installations support bridge idle cleanup, saved-machine connections to Linux and macOS also close their remote bridge after a minute without traffic in either direction. Sleep counts toward that deadline, which is checked when the host wakes. Quiet healthy connections exchange health checks; watching continuous output does not require typing. Cleanup leaves the remote Herdr server, sessions, and pane processes running. Older installations remain compatible without this optional cleanup.

Background connections never answer prompts or install, update, restart, or hand off a server. For non-authentication Attention, run the standalone setup command shown by Herdr in an interactive terminal, for example:

```bash
herdr --remote workbox
```

Use your profile's target. If you chose a named session when adding it, include the optional `--session <name>` here too. Follow the requested setup prompts; open clients retry automatically. `machine reconnect` does not install or update Herdr. Do not stop a running server merely because its version differs from the client.

If authentication fails, check ordinary SSH first. For a passphrase-protected key, load it with `ssh-add` before starting Herdr's non-interactive background connections.

For Git authentication or SSH signing inside remote panes, enable `ForwardAgent yes` for the trusted host in your SSH config. Herdr does not enable forwarding for you. When a session starts with an agent, updated Linux and macOS servers give panes a stable agent address, so existing and new panes can use the forwarded agent after `--remote` or a saved machine reconnects. A working inherited agent or earlier connection keeps priority over later clients and temporary setup checks; if it disappears, another live attachment can supply the agent.

This requires an updated remote server, not just an updated local client. Local sessions started without an agent leave `SSH_AUTH_SOCK` alone. Panes created before the server update, or before an agent was first supplied to the session, keep their original environment and need to be recreated once to inherit the stable address. Older compatible servers and connections without agent forwarding can still attach normally.

## Settings and automation

The UI uses the client's local theme, sidebar settings, and keybindings by default. Custom commands and plugins advertised by the selected server still run there. Herdr does not copy local command plugins, configuration, executables, or secrets onto SSH hosts. Missing remote commands fail visibly. Use the UI's `reload config` action after editing client settings; see [Configuration](/docs/configuration/#reload-config).

Default agent rows show a `machine` token when multiple machines are present. Existing custom rows are preserved; add `machine` explicitly if you want that label in your layout. [Sidebar row layouts](/docs/configuration/#sidebar-row-layouts) also support conditional colors for machine labels.

Workspace, tab, pane IDs, and agent names are scoped to one server. Two machines may both contain `w1:p1` or an agent named `reviewer`. Selecting a machine in the UI does not retarget CLI commands running in an existing pane: they still use that pane's inherited session and socket. For remote automation, use `herdr --machine <label-or-id> agent list`, then pass the same prefix when controlling those remote IDs. The CLI uses the saved profile's SSH target and session directly; it does not need an open TUI. Without `--machine`, existing session/socket routing is unchanged. See [CLI reference](/docs/cli-reference/#saved-ssh-machines) for supported commands, update requirements, and remote path rules.

## Updates and saved data

Saved profiles contain only an opaque ID, label, SSH target, explicit remote session, and enabled state. Herdr does not store passwords, private keys, agent tickets, or SSH control sockets in the catalog. Authentication stays with OpenSSH.

Herdr separately remembers each machine's remote OS and resolved executable path so repeated `--machine` commands can skip discovery. Existing profiles learn missing information on first use. This cache is optional: missing, invalid, or unwritable cache files do not prevent commands from working. Commands still check live server compatibility. If a cached executable is missing or no longer supports API forwarding, Herdr rediscovers it during the initial read-only check; it never automatically repeats a command that may already have changed remote state.

The client and server negotiate compatibility rather than requiring identical versions. Saved-machine connections additionally need the server's `surface_interest` and `health_check` capabilities. Older servers without those capabilities show Attention until explicitly updated, even if a standalone attach works. Other missing server methods disable only their corresponding actions.

Updating a compatible client does not replace the running remote server or stop its agents. When you need new server-side behavior, update that server explicitly. Normal replacement asks before stopping the server and its pane processes.

Live handoff is experimental and opt-in. For a supported server that needs replacement during standalone setup, you can explicitly add `--handoff` to `herdr --remote`; it is not needed for normal connections or authentication fixes. See [Update](/docs/install/#update) for restart and handoff choices, and [Session state and restore](/docs/session-state/) for what survives each operation.


## Private automatic updates through Redie

Private Mac builds can opt into signed automatic updates with one bootstrap:

```sh
cd ~/herdr
rsync -azvp --exclude='.git' --exclude='target' redie:~/herdr/ ./
cargo run --release -- updates enable
~/.local/bin/herdr
```

After enabling, launch `herdr` normally. Both Macs check for a published build
about once a minute using a dedicated private-update login job, even with their UIs closed. Older server-list sync jobs cannot replace this job. The UI provides a fallback when that job is unavailable; one worker owns automatic checks per state namespace. Enable reports success only after the expected binary and its updater confirm a fresh successful check. A running manager waits for its
setup dialog or navigation mode to close, then detaches and reconnects using the
updated executable. Runtime daemons and running terminal processes stay in place.
The sync details view includes the private update status and installed build.
Use `herdr updates status`, `check`, or `disable` to inspect, check immediately,
or opt out without disabling server-list sync.

The read-only Rust feed binds Redie's current Tailscale IP and serves only the
signed current manifest and content-addressed binaries. Clients verify a public
signing key pinned by the trusted source bootstrap, the exact signing namespace,
binary checksum and length, release counter, Mac architecture, and compatible
runtime/endpoint generations. Updates use no SSH credential; server-list keys
remain limited to their existing catalog operations. The signing private key
stays on the publishing Mac outside the repository. A previous executable is
retained at `~/.local/bin/herdr.previous` for manual recovery. Incompatible
runtime generations pause updating instead of stopping sessions.

Manual publication remains available after validation:

```sh
just build-linux-bundle
python3 scripts/publish_private_update.py target/release/herdr
```

The manager includes the matching Linux payloads. The publisher checks that its
source matches the build and uploads the complete immutable binary before
atomically switching the signed current manifest. Existing publications are
protected by a monotonically increasing release counter. Keep the prior signed
artifacts available while clients may still be downloading them.


On the feed host, `herdr updates peers` shows bounded client-reported diagnostics
by the actual Tailscale source IP, including the installed/running build, whether
checks are automatic, the last receipt age, and any reported error. Reports are
observations, not authorization to install or execute anything. A plain manifest
request alone is never treated as proof of installation. The feed accepts only
bounded report bodies with an absolute deadline, in addition to its immutable
artifact routes.


## Publish automatically after a private master push

With the private build worker installed, `git push redie master` is the complete
release action. Redie's post-receive hook queues the exact master commit. The
publishing Mac fetches that commit into a separate build checkout, runs
`just check` plus all-feature workspace tests, builds the manager with both
Linux payloads, and signs and publishes the result. Both managers then install
it through their existing automatic updater. Other branches and master deletion
do not publish releases. Unpushed workspace edits are never part of a build.

Install the worker once on the Mac holding the release signing key:

```sh
python3 scripts/private_build_worker.py install
```

This requires Rust, cargo-nextest, just, Bun, Node, Python 3.11+, and the Mac SDK on that Mac.
The queue helper and post-receive hook are installed on Redie; no signing private
key is copied there. Only trusted pushes to this private `master` should be
accepted: Cargo build scripts, macros, and tests execute as the publishing Mac's
user. This automation is not a sandbox for untrusted PRs or branches.

When the Mac is asleep, offline, or logged out, pushes remain queued on Redie.
When it returns, the newest master commit is built. Build caches persist between
runs. A newer accepted push supersedes an in-progress older build; publication
holds a Git reference transaction while checking the exact master commit and
atomically switching the signed manifest. Failed checks leave the last good
release active. Compiler/SDK/build-checkout variants get separate build IDs.

Inspect the queue, current stage, last successful build, and failure details:

```sh
python3 scripts/private_build_worker.py status
```

After correcting an infrastructure problem, retry the current commit with:

```sh
python3 scripts/private_build_worker.py retry
```

A new master push automatically retries changed code. Signing/publication outages
retry automatically; lint or test failures wait for a changed commit or an
explicit retry. Logs live in `~/.local/state/herdr/private-build-worker/logs` on
the publishing Mac. The existing checkout in `~/herdr` remains available for work.

The lower-left sidebar shows a small compiled version such as **v0.9.5 b42**,
with the sync indicator directly above it. The same signed binary displays the
same build number on every Mac. Redie reserves increasing build numbers before
automatic release builds; retries of the exact queued request reuse their
reservation. Failed builds can leave gaps, and the counter is never reset by
queue history cleanup. Build numbers are included in both Linux payloads and
the Mac manager. Unnumbered source builds display `dev` or a short build hash.
In a collapsed sidebar the label shortens to `b42` when it fits; expand it or
open sync details to see the full version.

The sidebar also shows **Updates: 2 current · auto** when both managers have
recently confirmed the latest signed release and automatic updates. Click the
sync or update indicator to open **Manager sync & updates**. Each computer's
name/IP, reported version, automatic update setting, and last report age appear
at the top. Missing or stale reports, disabled updates, errors, and pending
updates remain visibly unconfirmed. These are background updater diagnostics;
a UI with an open dialog can defer its restart until the dialog closes.

Status refreshes automatically through the existing background updater, even
with multiple UIs open. **Refresh manager status (Ctrl+R)** also refreshes the
host observation. Older update hosts must be upgraded to serve manager status;
older managers remain compatible and show an unknown version until upgraded.

Expanded sidebars also show the first two managers directly above the sync
indicator: each computer's name, version and automatic update setting. A green
check marks a fresh report matching the latest signed release; `?` marks stale
or missing confirmation. Narrow cards shorten the version to its complete build
number. Short windows and collapsed sidebars retain the compact indicators;
expand the sidebar or enlarge the window to show both manager cards.

Each manager card shows a compact check-in age such as **35s** beside its
version and automatic update setting, without a separate “Seen” row. A report
older than 150 seconds is marked **stale**. **host stale** means the update
host's observation is no longer fresh; it does not establish that a particular
Mac is offline. Missing check-ins show **?**. Narrow cards shorten the version
to its complete build number; at extreme widths the age moves beside the name
so the build number and automatic update setting stay readable.

**Add server** opens the online Tailscale device list immediately. Type to
search, then select a device or press Enter to connect and set it up. Herdr
fills the device's address and name, enables automatic SSH-key setup, and
suggests a username when enabled saved servers agree on one. Click Username
or press Tab to edit it; leave it blank to use SSH configuration or your local
username. Password and installation approvals remain inside the TUI.

Choosing a device already saved for that username reconnects its existing
profile instead of adding a duplicate. If several saved sessions match, choose
the desired saved server. **Manual / advanced** remains available for other
addresses, ports, keys, and session settings. Browsing devices does not connect
to or install anything until you select one.

To add several devices, click their checkboxes or move with ↑/↓ and press
Space, then choose **Add selected** (or press Enter on a device row). Search and
Refresh preserve selections by Tailscale device ID. **Select all online** selects
new devices matching the current search, up to 32 per batch. Saved servers show
**added** and are skipped, including entries saved under another username or IP
alias and disabled entries. Herdr checks again just before SSH setup, so a server
that arrives through sync while queued is skipped too. A selected device that
disappears or is replaced is skipped. Select All itself never starts setup.

Herdr sets up one server at a time, showing the current server and progress.
The Username field is captured for the batch; each server uses its own SSH
authentication and installation approvals. Passwords are neither retained nor
replayed across servers. A failure does not stop the remaining servers.

The results screen lists every outcome. Choose a failed server to inspect its
retained setup output, or **Retry failed / stopped servers** to retry only those
entries. Up to eight bounded failure screens are kept in memory for this dialog.
Cancel stops the current setup and remaining queue; completed servers stay
saved and running. Closing the dialog discards the queue. Choose a saved server
explicitly from Servers to reconnect or change it.


## Create cloud servers

Open **Servers → Cloud instances**, or **Cloud instances** in the online-device
browser. The panel runs inside Herdr's existing setup terminal. Choose a numbered
option and press Return; Ctrl+G closes it. No separate shell is needed for normal
account setup or instance actions.

Configure AWS accounts/profiles and regions, or Google accounts/configurations,
projects and zones in this panel. The official AWS CLI v2 or Google Cloud CLI
must be installed on the manager computer; account configuration can launch
provider sign-in inside the panel. Accounts and provisioning jobs are local to
that computer. Provider credentials and SSH private keys are never synced.

Configure Tailscale once with an OAuth client authorized for `auth_keys` write
and the chosen server tag. Enter its secret in the hidden input in Herdr. It is
stored in a private local file; the VM receives a single-use, 24-hour enrollment
key. Tailnet policy must permit the manager to reach tagged servers on SSH.
The provider retains user data/startup metadata, including this short-lived key;
Herdr never places the long-lived OAuth secret there.

Choose **Create AWS EC2**, **Create AWS Nitro Sandbox**, or **Create Google Cloud**.
Review the account, location, image, size and network, then type `CREATE`.
Resources incur provider charges. The selected subnet must have outbound internet;
this initial implementation assigns an external address for egress and blocks
public SSH. AWS requires an existing security group with no inbound rules.
GCP creates an owned IPv4 SSH deny rule; organization policies that disallow
metadata SSH keys or external addresses can prevent setup.

Herdr installs Tailscale, verifies its node against the authenticated provider's
serial console, pins its Ed25519 SSH host key, and installs the current bundled
Rust server. It saves the server only after the health check passes, then normal
server-list sync shares the entry with other managers. SSH access remains local:
other managers need their own authorized SSH key and host trust.

**Manage / resume existing jobs** retains the provider identity and exact create
request across failures. Resume reconciles an existing resource before retrying
an uncertain create; retries use the original idempotency token within a bounded
window. It refuses to replay an unknown create after that window expires.
**repair-enrollment** refreshes an expired first-boot key for a job that has never
become Ready. It stops/restarts an EC2 parent and can repair a Nitro guest's
bootstrap disk. **Start**, **Stop**, and **Delete** require explicit review.
Stop ends running programs and retains billable disks; Delete removes the owned
instance/boot disk and GCP firewall rule. Shared networking is left intact.
Closing the setup panel retains created resources for Manage; it does not delete
them or finish a cancelled local installation.

Nitro provisioning creates a dedicated compatible AL2023 kernel 6.18 EC2 parent
and one Firecracker 1.18 guest. The guest uses persistent root storage, an owned
TAP/NAT network with parent IMDS blocked, and its own Tailscale/SSH identity.
The parent reserves memory and reboots during initial preparation. This is a
**direct-mode sandbox with console diagnostics**, without confidential attestation
or secret-release guarantees. An overlapping guest subnet is rejected before
network changes. Stop/start reconstructs the guest network and preserves its disk.
Live provider provisioning requires account credentials and has to be validated
in the chosen account before relying on it for production workloads.
